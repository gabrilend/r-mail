## Recent work, oldest to newest

1. **Treating received attachments as untrusted input (late September).** A file
   sent by a contact is now handled as possibly hostile:
   - A symbolic link inside a contact's zip becomes a text note saying where it
     pointed. It is never created as a real link.
   - Every piece of an attachment carries its checksums, and the total number of
     pieces is fixed by the first piece.
   - A file that changes on disk while it is being packed is packed again on the
     next cycle, so a half-written copy is never sent.
   - A contact cannot choose a folder name that climbs out of rmail's own
     folders, and nothing is accepted before you say yes.
   - A zip may not unpack to more than its sender declared.
   - rmail now packs and unpacks zips with the shared zip library and no longer
     runs the outside `zip`/`unzip` programs.
2. **Checking the documents against the code (October 2).** Each guide was
   compared with what the code actually does: README, protocol, encryption,
   attachments, scripting, helpers, router, NixOS service, thin client, Android
   and ports. The guides were corrected, and the gaps found became six new
   issues, 406–411.

## Work in progress, not committed

Four issue files have edits from the October 2 conversation. They record
decisions you made about attachments:

- **A recipient's answer belongs to the file's path, not its contents.** If
  someone declines `photo.jpg`, they are never offered `photo.jpg` again. You
  said: "We shouldn't be able to edit attachments, I don't think."
- **Each recipient's answers go in the existing outbox record.** No new files
  are added. The record keeps one answer per attached path: offered, complete,
  declined or cancelled. One shared place is needed because the packed copy can
  be deleted only once every recipient has answered.
- **Deleting an `attach:` line withdraws the file.** Each recipient who doesn't
  yet have the whole file gets a "no more of this attachment" message. Their
  daemon throws away the pieces it holds and leaves a notice. Anyone who already
  has the whole file keeps it.
- **The packed copy has to be kept on disk until everyone has answered.** Right
  now it lives in `/tmp`, which is RAM on your machine, and it is deleted as
  soon as the last active transfer finishes. So a recipient reached later, or
  anyone after a reboot, gets a fresh packing of whatever is at that path now.
  That means edits currently get through. This is a real bug today, not just a
  planned design.

## Bugs found by the audit, still open

- **An edited message can silently never arrive.** The daemon records the new
  version as "sent" before it sends anything. If the contact is offline or not
  due yet, the edit is lost for good and the recipient keeps the old version.
- **Cancelling one attachment deletes the whole message** for that recipient.
- **When a transfer finishes for the first recipient, the `attach:` line is
  removed**, so recipients reached later never get the file.
- **The health check doesn't say which contact it is about**, and **saving
  contacts on the phone erases the comments in that file.**
