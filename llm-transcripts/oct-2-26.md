I'd use one file, and it already exists. The program keeps a hidden record of
every sent message, `outbox.json` in its state folder, and that record already
has a section for each recipient. Right now each recipient's section holds only

that section:

- **Last version delivered**: a checksum of the text that person last confirmed
  receiving. This fixes the lost edits. The program sends an update to everyone
  whose checksum doesn't match the current file, and keeps retrying each person
  on their own timer until it gets through.
- **Attachment answers**: for each attached file, one word: offered, complete,
  declined or cancelled. This fixes the other three bugs. A file is offered to a
  person only if they have no answer yet. Cancelling changes only that word, not
  the message. The `attach:` line is never erased, so someone who was offline
  still gets the file later.

The outbox message itself stays exactly as the author wrote it. It's your copy,
and the program stops editing it. You get no extra files to look at. The record
is in the same place it is now, just more detailed.

One file per recipient doesn't add much. Each recipient's details would still
need to point back to the shared message and the shared packed zip. The zip can
only be deleted once every recipient is complete or has declined, and that's
easiest to check when all their answers are in one place.

I've written your decision into the issue files. Nothing is committed and no

**What deleting an `attach:` line will do:**
- The program stops sending pieces of that file to anyone.
- It sends a "no more of this attachment" message to everyone who doesn't have
  the whole file yet. That includes people who haven't answered and people
  partway through receiving it.
- People who already have the whole file keep it, and nothing is sent to them.
- If a recipient is offline, the program keeps trying on their contact's timer
  until it gets through, the same way edits will be retried.
- When the message arrives, the recipient's program throws away the pieces it
  has, removes the consent form, and leaves a note saying you withdrew the file.
- Once nobody needs the packed copy anymore, it's deleted.

**One message, both directions.** The cancel issue already needed a new message
meaning "cancel this one attachment" for when a recipient cancels. Your
withdrawal uses that same message going the other way. Whichever side stops, the
other side stops that one transfer and never touches the message itself. It
travels encrypted like everything else, so you don't need a separate plain web
address for it. Someone watching the network can't see which file was withdrawn.

Your decision changes one thing from earlier: the outbox file is no longer just
your copy of the message. The program now reads it to decide what to send, at
least for attachments.
