## The issue: one crashing step freezes the whole mailbox

## How a sync works today

The daemon runs a loop. On each pass it asks one question: is any contact due to
be contacted? If yes, it runs a sync. If no, it sleeps until the soonest due
time.

Each contact has a small timer record:

| field | type | meaning |
|---|---|---|
| interval | number (seconds) | how long to wait after the last attempt; starts at 30, grows by 360 on each failure, capped at 2 hours |
| next due | number (Unix time, seconds with a fraction) | when this contact is next worth trying |
| last success | number (Unix time) or empty | when they last answered |

The mailbox also keeps one extra timer for itself, which keeps a mailbox with no
contacts ticking.

A sync then goes in two parts:

1. **Seven steps of work, in a fixed order:** send new and changed outbox
   messages, sync the inbox, send address-change notices, check pending
   attachment consents, send consent answers, send attachment pieces, send
   attachment cancellations. While these run, each network attempt only *notes
   down* whether it reached the contact, in a scratch table of contact name
   (text) → reached this cycle (true/false). Timers are deliberately not moved
   yet. This was a design choice: six messages queued for one unreachable
   contact should count as one failure, not six.
2. **Bookkeeping, once, at the end:** it reads that scratch table and moves each
   contact's timer. Contacts reached go back to 30 seconds; contacts that failed
   back off. Contacts with nothing to send get pushed 30 seconds ahead. The
   mailbox's own timer moves too. Last comes the one-line "unreachable contacts
   this cycle" summary.

The whole sync is wrapped in a single safety net. If anything inside it throws
an error, the error is caught, one "sync error" line is logged, and the loop
carries on.

## What goes wrong

The safety net sits around the whole sync, not around each part. So an error in
step 6 means:

- **Steps 7 and the bookkeeping never run.** No timer moves. Every contact whose
  time had come stays "due now", including contacts that were reached
  successfully in steps 1–5.
- **The loop sees "someone is due" again at once** and sleeps for zero seconds.
  The next sync hits the same error in the same place, so it keeps repeating.
- **Every step after the broken one is starved.** Yesterday it was step 6, so
  only cancellations were blocked. If the broken record had been in step 1 (the
  outbox), incoming mail, address notices and attachments would all have stopped
  too.
- **Steps before the broken one repeat on every pass.** That's my best
  explanation for "notified kuvalu-notes of address change" appearing on every
  line pair: step 3 ran again each time and nothing ever marked it finished. I
  haven't proven this part.
- **The error message loses its location.** The safety net keeps only the last
  line, so the log said "line 302", which is the file-existence helper, not who
  called it. That's why finding the cause yesterday took a trip through the
  state files instead of reading one log line.
- **The log fills.** How fast depends on how long each pass takes. In your
  mailbox kuvalu-notes answered instantly and sorelu refused instantly, so
  passes took a fraction of a second: several crashes per second, 200 MB
  overnight. In the test, the fake contact's address took seconds to time out,
  so crashes came about every 30 seconds.

That corrects my earlier guess: the android contact wasn't the reason. The speed
came from how quickly each network attempt ended.

## What it should do

- **A broken step only breaks itself.** Each of the seven steps gets its own
  safety net. When one fails, it logs which step failed, with the full chain of
  calls that led there, and the other six still run.
- **Bookkeeping always runs.** Timers move and the summary is written whether or
  not a step failed.
- **A step that keeps failing is reported where you'll see it, not a million
  times in a log.** Following the pattern the daemon already uses when it can't
  open its port: log the first failure, then log a count instead of repeating
  it. Also leave a notice file in the mailbox's own inbox naming the step and
  the error, and remove it once the step succeeds again.

This isn't a fallback. The error still stops the broken step every time and is
reported louder than today. The change is that it stops *only that step*.

  section) and then asked. An issue with an unanswered question is in
  progress, not done.

## Splitting into sub-issues

Split when an issue holds work streams that could be built, tested or reviewed
separately, or when it cannot be finished in one sitting. Do not split an issue
that is already one mechanism. When splitting, produce and then write out:

1. **A table** — `| ID | Name | Dependencies | Description |`, where ID is the
   parent number plus a lower-case letter (103a, 103b), Name is dash-separated
   lower-case words, Dependencies is "None" or sibling IDs.
2. **The rationale** — the distinct work streams, why one issue cannot hold
   them, what splitting buys.
3. **The execution order** — a small dependency graph, e.g.
   `103a (foundation) → 103b (needs 103a) → 103c (parallel with 103b)`.

Each row becomes a file `{parent}{letter}-{name}.md` with the three sections.
The parent keeps its blueprint and gains a short list of its sub-issues; the
analysis itself is not appended to the parent (that would be worklog, not
blueprint). Run `validate-issues` afterwards: it reports orphaned sub-issues
and one-sided links.

## Completing an issue

An issue is complete only when nothing in it is deferred and no open question
is unanswered. Then, in this order:

1. **Run the project's tests.** A fixed bug gets a test that would have caught
   it.
2. **Rewrite the issue as the blueprint of what was built**: Current Behavior
   states the built system; steps name the real functions and files; decisions
   not taken are stated with their reason. Poetry the owner wrote during the
   work goes into the issue verbatim.
3. **Move it** into `issues/completed/` (`git mv`, so the history follows).
4. **Update `issues/phase-<N>-progress.md`** for that phase. Take counts from
   `progress-dashboard.lua <project> -m`, or better, name the command instead
   of copying numbers that will go stale.
5. **Update related issues** whose Current Behavior or assumptions changed.
6. **Run `validate-issues <project>`** and fix new findings that the change
   caused. Findings older than the change are reported to the owner, not
   silently fixed in passing.
7. **Commit** as below.

## Committing

The rule (CLAUDE.md): a commit carries exactly the lines this session wrote —
never another session's work, even if it sits in the same file — and this
conversation's transcripts ride along.

Commit small and often: each piece as soon as it is done and checked, not a
pile at the end.

1. Optionally preview: `stage-own-changes <repo>` lists what would be taken
   and what left out, and writes nothing.
2. Commit: `commit-own-changes <repo> -F -` with the message on standard
   input. It builds the commit on a private staging list from this session's
   own lines (the edit ledger the edit hook keeps) and its transcripts, and
   never touches the shared staging area, so nothing another session has staged
   can ride along. Plain `git commit` is refused by the commit gate.
3. Message style: say what the software now does, in plain English and by
   mechanism or analogy; mention any extra changes and why. No function names.

**When it stops or leaves something out.**

- **A tangled ("mixed") block** means another session changed lines right
  next to or on top of yours. Nothing is committed. Tell the owner which file
  and line; decide together what that region should say. `--leave-mixed`
  commits your other blocks meanwhile.
- **Lines that are yours but were written by a route the ledger could not see**
  (a script you ran, a generator, `sed`, a rename): record them with
  `claim-own-change <file>` and say so in the commit message.
- **A warning about the shared staging area** means someone had staged that
  file by hand in a way that overlaps your commit; their entry was left alone.
  Tell the owner.

The one-time permission tokens (`/tmp/claude-allow-*`) belong to the person.
Never create one; if a gate names a token, relay the gate's message and let
the owner decide.

## Is editing two-way?

You're right: **deletions go both ways, edits go one way.**

- **You edit a message in your outbox:** the daemon notices the text changed and
  sends the new version to each recipient. Their inbox copy is overwritten.
  Their `on_update` hook can reshape it first.
- **A recipient edits their inbox copy:** nothing happens. The daemon doesn't
  watch inbox files for edits, only for deletion. And your next edit overwrites
  whatever they changed.
- **Deletions, both ways:**
  - you delete the outbox file, and their inbox copy is deleted;
  - they delete their inbox copy, and your daemon is told, then takes them off
    that message's `to:` lines.

So there's no back-and-forth inside one file. A reply is a new message.

## The lost-edit bug is worse than I said

It doesn't only lose the edits in between. It can lose the **final** version.
After checking an outbox message for changes, the daemon records "this is the
text I've sent" unconditionally, whether or not the update went out. If the
recipient wasn't due for contact yet, or didn't answer, the update is dropped
and never retried. Their copy stays at the older version until you happen to
edit again at a moment when they're reachable.

The fix is small and fits your "final result matters" rule: record the text as
sent to each recipient only once that recipient has actually received it. Then
the latest version always gets there eventually, and the in-between versions can
still be skipped.

  # Part B — Networking and connection management

  ## Phone to home daemon (`net/RmailClient.kt`, `crypto/Crypto.kt`)
  - **Transport:** raw TCP with no TLS.
    - **Frame format:** `[4-byte big-endian length][12-byte random nonce][AES-256-GCM ciphertext + 16-byte tag]`, with a 16 MB cap per frame.
    - **Key:** `SHA-256(token)`. The token is a pre-shared secret.
    - **Plaintext inside:** HTTP/1.0-style text — request line, `Content-Type`, `Content-Length`, optional extra headers, blank line, body.
  - **Connection:** one persistent keep-alive connection. It reconnects and
    retries once on an `IOException`. The connect timeout is 5 s and the read
    timeout is 30 s (raised from 10 s in #320). The daemon keeps an idle
    keep-alive connection open for 30 s.
  - **Sender identity:** the daemon works out who is calling by trial decryption
    — it tries every contact's key. After the first request on a connection it
    reuses the key that worked.
  - **`X-Mtime`:** sent in both directions, so file modification times
    (authoring order) survive the copy.
  - **Endpoints** (all under `/api/`, own devices only):
    - `POST /api/sync`
    - `GET /api/file/{inbox|outbox}/<f>` and `POST /api/file/outbox/<f>`
    - `GET` and `POST /api/contacts`
    - `POST /api/consent`
    - `GET /api/attachments`, plus `/…/<f>/info`, `/…/<f>/chunk/<n>`, and `DELETE /api/attachments/<f>`
    - `POST /api/upload/start`, `POST /api/upload/resume`, `PUT /api/upload/<id>/chunk/<n>`
    - `GET /api/myaddress` (the daemon's public IP, LAN IP, IPv6 and name)
    - `POST /api/log`
  - **Endpoints between daemons:** `POST /deliver` (with a `type` of message,
    update, attachment_request, attachment_response, and others), `POST
    /delete`, `POST /update-address`, `GET /peer-address`. A plaintext `GET /`
    health check answers `{"ok":true,"name":…}`.
  - **Chunked transfers:** 256 KiB chunks.
    - Uploads: the file is zipped, split into chunk files on disk, each chunk hashed with SHA-256, and `upload/resume` returns the list of chunks still missing, so an interrupted upload resumes.
    - Downloads: up to 2–64 chunks in parallel (sized to free memory). Each chunk is checked against its SHA-256 with up to 3 retries, then the whole file is checked.
  - **`SyncManager.sync()`:**
    - Runs under a process-wide `Mutex`, so the app and the background worker never sync at the same time.
    - **Host choice (`HostPicker`):** it first probes LAN addresses on the phone's own /24 (1 s timeout), then public addresses (3 s), and remembers the winner until the next sync.
    - **Order of a cycle:** pending attachments are uploaded first, and each `attach:` line is rewritten to its server path. The phone then sends a list of what it has (its inbox ids, deleted inbox entries, outbox filenames, deleted outbox files, and a hash of its contacts file). The server replies with lists of what to fetch and what to remove. Files are downloaded or uploaded, and the contacts file is merged.
    - **State is saved step by step (#386):** after every transfer the server confirms, the phone writes its state right away, so a failure later in the cycle never re-sends finished work. Before this, a failure anywhere discarded the record, and one run uploaded 44 files 65 times.
    - **Notifications:** new mail posts a local notification.
  - **Polling cadence (`sync/SyncBackoff.kt`):** the same numbers as the daemon
    — floor 30 s, +360 s per failure, 2 h ceiling, ±30 s jitter.
    - The poll loop runs while the app is in the foreground (`MainViewModel.startForegroundPolling`).
    - Any local write (send, delete, contact edit) calls `triggerSync()` at once, ignoring backoff.
    - Arriving mail calls `resetNow()`, so the next poll happens immediately.
    - In the background, **WorkManager** `SyncWorker` runs a periodic job (minimum 15 minutes) that syncs every mailbox.

  ## Daemon to daemon (`rmail.lua`)
  - **Contacts file:** `name.field = value` lines; text values in quotes.
    Fields:
    - `ip` — the default address, tried first and never reordered.
    - `ip[N]` / `port[N]` — extra addresses. When a non-default one succeeds, it is moved to the front (`promote_contact_index`).
    - `local-ip` / `local-ip[N]` — LAN addresses, tried before everything else, but only when they share our /24.
    - `ipv6`, `port`, `token`, and `own = true` for a person's own devices.
    - Hostnames are allowed and resolved with a 60 s DNS cache.
    - `align_contacts` groups each contact's lines together and lines up the `=` signs.
  - **Per-contact timers (#377, the `ctimer` table):** floor 30 s, +360 s steps,
    2 h ceiling, ±30 s jitter taken from /dev/urandom.
    - **The gate:** every outgoing request passes through `http_post_batch_with_fallback`. Requests to a contact who isn't due yet are held back without being dropped.
    - **One outcome per contact per cycle:** the timer moves once per cycle for each contact, so six failed messages count as one failure.
    - **Reset on inbound:** `ctimer.saw_inbound` makes a contact due immediately when they send us a request we can decrypt.
    - **No expiry:** failed operations are backed off but never discarded.
    - **Startup:** every contact is due immediately.
  - **Batching:** one sync cycle (`run_sync_cycle`) runs seven builders —
    outbox, inbox deletions, address notices, consent checks, consent answers,
    attachment chunks, cancellations. Each builder sends its requests in
    parallel: non-blocking connects over `select`, an 8 s deadline, one request
    per connection. If the first attempt at connecting fails, the other
    addresses are tried one after another.
  - **LAN discovery:** multicast group `239.192.82.77` on the contact's port
    with TTL 1, **plus** a unicast sweep of the whole /24.
    - The message is an encrypted `RMAIL-DISCOVER <port> <lanip>`, answered with `RMAIL-HERE <lanip>`. The packet carries no name; the key that decrypts it identifies the sender (#393).
    - Discovery is sent at startup and whenever a connection to a same-house contact (one whose public IP equals ours) times out.
  - **Same network / hairpin:** when a contact's public IP is ours,
    `resolve_lan_host` swaps in their LAN address. A contact's LAN address
    learned from an incoming connection is kept only if it is on our /24;
    otherwise the connection came through a router relaying it (a hairpin), so
    the address is logged and ignored. `validate-router-settings.sh` tests
    whether the router supports hairpinning.
  - **Address announcements (#388):** `/update-address` carries `ip`, `port`,
    `ips` (hostname, public IPv4, global IPv6) and `local_ips` (sent only to
    contacts on our LAN).
    - The receiver merges the set and preserves hostnames and private addresses it may not overwrite.
    - It rewrites the contacts file only if the set of addresses actually changed. This prevents two daemons ping-ponging announcements forever.
    - It drops a hidden `.address-update-<name>` notice in the inbox, which is removed the first time we successfully send to that contact at the new address.
    - The daemon also announces itself to every contact at each startup.
  - **Public IP detection:** DNS-based, via OpenDNS, Cloudflare CHAOS TXT and
    Google TXT, in random order. A change is confirmed by a *different provider*
    before it is announced.
    - IPv6 comes from `ip -6 addr` (global, non-temporary). The daemon listens on a separate IPv6 socket (v6-only).
    - The LAN IP is also checked; if it changed, a notice about the port-forward goes to the inbox.
    - **Recheck (#379):** every 24–48 h, redrawn from /dev/urandom after every check so it drifts through the day. If no provider answers, it retries in 1 h.
  - **NAT / UPnP:** with `auto_port_forward = true` the daemon tries UPnP, then
    NAT-PMP, and renews the mapping every 30 minutes. The README carries a
    strong security warning.
    - `nat.security_check` runs at every startup. If the router accepts UPnP or NAT-PMP mappings, it writes an outbox message `SECURITY-WARNING-insecure-nat` to all non-own contacts, and later `SECURITY-RESOLVED-nat-fixed`.
  - **Problems reported as mail (#382, `report_problem`/`clear_problem`):** one
    file per problem, rewritten rather than appended, and stamped as written by
    the daemon.
    - Inbound problems go to the inbox (for example `CANNOT-LISTEN`); outbound problems go to the outbox.
    - A problem that goes away removes its own file.

  ## Latency: push or polling?
  - **Between daemons it is push, with a gate.**
    - Saving a file into the outbox (including the phone's upload) wakes the daemon's `select` at once through inotify and runs a sync cycle.
    - The `/deliver` goes out immediately **if that recipient's timer is due**. That is true after about 30 s idle (jittered 0–60 s), or right away if they just contacted us.
    - Otherwise it waits until the timer comes due: up to about 60 s for a healthy contact, and up to 2 h for a backed-off one.
    - Known stall: the sync cycle blocks the loop, so one dead contact can delay incoming requests by up to 8 s (#387).
  - **Daemon to phone is polling only.** There is no FCM and no socket held open
    between syncs.
    - In the foreground: a poll every 30 s ±30 s, and immediately after new mail arrives.
    - In the background: at least 15 minutes, via WorkManager.
  - **Phone to phone in the best case:** the sending phone syncs instantly, the
    two daemons pass the message in under a second on a healthy link, and it
    then waits for the receiving phone's next poll — typically 0–60 s with
    the app open, and 15+ minutes when closed.
  - Issue #389 (wake-to-sync windows) and the notes in
    `docs/connection-suggestions.md` about a permanent, always-open TCP
    connection are ideas only; neither is built.
