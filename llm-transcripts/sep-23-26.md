## The issue: one crashing step freezes the whole mailbox

## How a sync works today

The daemon runs a loop. On each pass it asks one question: is any contact due to
be contacted? If yes, it runs a sync. If no, it sleeps until the soonest due
time.

Each contact has a small timer record:

| field | type | meaning |
|---|---|---|
| interval | number (seconds) | how long to wait after the last attempt; starts at 30, grows by 360 on each failure, capped at 2 hours |
| next due | number (Unix time, seconds with a fraction) | when this contact is next worth trying |
| last success | number (Unix time) or empty | when they last answered |

The mailbox also keeps one extra timer for itself, which keeps a mailbox with no
contacts ticking.

A sync then goes in two parts:

1. **Seven steps of work, in a fixed order:** send new and changed outbox
   messages, sync the inbox, send address-change notices, check pending
   attachment consents, send consent answers, send attachment pieces, send
   attachment cancellations. While these run, each network attempt only *notes
   down* whether it reached the contact, in a scratch table of contact name
   (text) → reached this cycle (true/false). Timers are deliberately not moved
   yet. This was a design choice: six messages queued for one unreachable
   contact should count as one failure, not six.
2. **Bookkeeping, once, at the end:** it reads that scratch table and moves each
   contact's timer. Contacts reached go back to 30 seconds; contacts that failed
   back off. Contacts with nothing to send get pushed 30 seconds ahead. The
   mailbox's own timer moves too. Last comes the one-line "unreachable contacts
   this cycle" summary.

The whole sync is wrapped in a single safety net. If anything inside it throws
an error, the error is caught, one "sync error" line is logged, and the loop
carries on.

## What goes wrong

The safety net sits around the whole sync, not around each part. So an error in
step 6 means:

- **Steps 7 and the bookkeeping never run.** No timer moves. Every contact whose
  time had come stays "due now", including contacts that were reached
  successfully in steps 1–5.
- **The loop sees "someone is due" again at once** and sleeps for zero seconds.
  The next sync hits the same error in the same place, so it keeps repeating.
- **Every step after the broken one is starved.** Yesterday it was step 6, so
  only cancellations were blocked. If the broken record had been in step 1 (the
  outbox), incoming mail, address notices and attachments would all have stopped
  too.
- **Steps before the broken one repeat on every pass.** That's my best
  explanation for "notified kuvalu-notes of address change" appearing on every
  line pair: step 3 ran again each time and nothing ever marked it finished. I
  haven't proven this part.
- **The error message loses its location.** The safety net keeps only the last
  line, so the log said "line 302", which is the file-existence helper, not who
  called it. That's why finding the cause yesterday took a trip through the
  state files instead of reading one log line.
- **The log fills.** How fast depends on how long each pass takes. In your
  mailbox kuvalu-notes answered instantly and sorelu refused instantly, so
  passes took a fraction of a second: several crashes per second, 200 MB
  overnight. In the test, the fake contact's address took seconds to time out,
  so crashes came about every 30 seconds.

That corrects my earlier guess: the android contact wasn't the reason. The speed
came from how quickly each network attempt ended.

## What it should do

- **A broken step only breaks itself.** Each of the seven steps gets its own
  safety net. When one fails, it logs which step failed, with the full chain of
  calls that led there, and the other six still run.
- **Bookkeeping always runs.** Timers move and the summary is written whether or
  not a step failed.
- **A step that keeps failing is reported where you'll see it, not a million
  times in a log.** Following the pattern the daemon already uses when it can't
  open its port: log the first failure, then log a count instead of repeating
  it. Also leave a notice file in the mailbox's own inbox naming the step and
  the error, and remove it once the step succeeds again.

This isn't a fallback. The error still stops the broken step every time and is
reported louder than today. The change is that it stops *only that step*.

## Before writing a new issue

1. **Search first, including `issues/completed/`.** Grep the issue tree for
   the feature's nouns, not just the likely title. A completed issue about the
   same machinery is reopened and extended rather than duplicated: history is
   more useful stacked vertically in one file than spread across several.
2. **Pick the phase by what the work builds on**, not by when it is being
   done. Lower numbers are foundations; later issues depend on earlier ones.
3. **Take the number from the tool:** `validate-issues <project> --next
   <phase>`.
   It reads the project's own naming shape (522, 1001, 9-007, A04) and never
   reuses a number that a completed file already holds.
4. **Write the blueprint** with the three sections CLAUDE.md requires, plus
   link fields in the shape the project already uses (look at a neighbour).
   Name related functions, structures and files instead of pasting code.
5. **Check it:** `validate-issues <project> --file <new-issue>`, and fix what it
   reports on the new file. If the new issue blocks or is blocked by others,
   add the matching line to the other side too.

## While working

- Keep **Current Behavior** true. It is the only section that changes while
  an issue is in progress; rewrite it in place rather than appending a log.
- A question that surfaces is written into the issue (an "Open questions"

## Splitting into sub-issues

Split when an issue holds work streams that could be built, tested or reviewed
separately, or when it cannot be finished in one sitting. Do not split an issue
that is already one mechanism. When splitting, produce and then write out:

1. **A table** — `| ID | Name | Dependencies | Description |`, where ID is the
   parent number plus a lower-case letter (103a, 103b), Name is dash-separated
   lower-case words, Dependencies is "None" or sibling IDs.
2. **The rationale** — the distinct work streams, why one issue cannot hold
   them, what splitting buys.
3. **The execution order** — a small dependency graph, e.g.
   `103a (foundation) → 103b (needs 103a) → 103c (parallel with 103b)`.

Each row becomes a file `{parent}{letter}-{name}.md` with the three sections.
The parent keeps its blueprint and gains a short list of its sub-issues; the
analysis itself is not appended to the parent (that would be worklog, not
blueprint). Run `validate-issues` afterwards: it reports orphaned sub-issues
and one-sided links.

An issue is complete only when nothing in it is deferred and no open question

1. **Run the project's tests.** A fixed bug gets a test that would have caught

## Committing

The rule (CLAUDE.md): a commit carries exactly the lines this session wrote —
never another session's work, even if it sits in the same file — and this
conversation's transcripts ride along.

Commit small and often: each piece as soon as it is done and checked, not a
pile at the end.

1. Optionally preview: `stage-own-changes <repo>` lists what would be taken
   and what left out, and writes nothing.
2. Commit: `commit-own-changes <repo> -F -` with the message on standard
   input. It builds the commit on a private staging list from this session's
   own lines (the edit ledger the edit hook keeps) and its transcripts, and
   never touches the shared staging area, so nothing another session has staged
   can ride along. Plain `git commit` is refused by the commit gate.
3. Message style: say what the software now does, in plain English and by
   mechanism or analogy; mention any extra changes and why. No function names.

**When it stops or leaves something out.**

- **A tangled ("mixed") block** means another session changed lines right
  next to or on top of yours. Nothing is committed. Tell the owner which file
  and line; decide together what that region should say. `--leave-mixed`
  commits your other blocks meanwhile.
- **Lines that are yours but were written by a route the ledger could not see**
  (a script you ran, a generator, `sed`, a rename): record them with
  `claim-own-change <file>` and say so in the commit message.
- **A warning about the shared staging area** means someone had staged that
  file by hand in a way that overlaps your commit; their entry was left alone.
  Tell the owner.

The one-time permission tokens (`/tmp/claude-allow-*`) belong to the person.
Never create one; if a gate names a token, relay the gate's message and let
the owner decide.
