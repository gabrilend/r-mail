**What's happening**

- **Where it started.** In April you queued `~/pictures/victory-garden.jpg` for
  sorelu in the `atch-test` message. The daemon saved a record of that transfer
  in `~/mail/.state/chunks-outgoing.json`: a text file listing the attachment's
  name, the path to the original picture, who it's for, and which pieces are
  still unsent. Before sending, the picture gets packed into a temporary
  compressed copy in RAM. At that time the record stored an ID for that copy,
  not its location.
- **The April change.** Two days later the code switched to storing the copy's
  location instead. The commit message said older records without a location
  would be fixed automatically: on the next send, the daemon would see "no
  compressed copy" and make a new one from the picture.
- **Why that didn't happen.** Before building a new copy, the daemon asks "does
  the compressed copy exist?" That check can't handle a record with no location
  at all. Instead of answering "no", it crashes. So the rebuild step never runs,
  even though the picture is still where it was.
- **When it surfaced.** The transfer sat waiting for sorelu's approval until
  yesterday at 14:02, when sorelu approved it. That's why the error only showed
  up then.
- **Why it's a fast loop, not one error.** Each sync runs seven steps in order,
  and sending attachment pieces is step 6. The step that sets when to next
  contact each person runs after all seven. Because the crash stops the sync
  before that, every contact always looks overdue, so the daemon never waits
  between syncs. That's how `/tmp/kuvalu-mail.log` grew to 200 MB with over a
  million identical errors. One stuck picture is holding up all mail from
  `~/mail`, not just the picture.

I'm not sure why the "notified kuvalu-notes of address change" message repeats
