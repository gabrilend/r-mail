## Three problems with putting the machine half in the service file

**Hand-launching loses its port.** The QA tester guide starts three daemons by
hand with no service involved, and your portable drive's launcher isn't a system
service either. If the port only exists in a service file, everything not
started by a service has no port. Related, and worse: I found that the daemon
currently does `config.port or 8025` — a **silent fallback to 8025**. By your
own rule that's a warning, therefore an error. Right now a config with a typo'd
port key gets you a daemon on 8025 and no complaint, which on this machine would
collide with `kuvalu`.

**The installer's port-collision check gets weaker, maybe unworkable.** It
currently reads every sibling config to see which ports are taken. Move ports
into service files and it must instead parse five formats — systemd user,
systemd system, runit, OpenRC, NixOS — several living in root-owned
directories, under a standing constraint that the installer never escalates
privileges. And at the moment it picks a port, the service file *doesn't exist
yet*: the installer generates one and prints instructions for you to install it.
It would be checking against a record that isn't written.

**The portable drive gains nothing.** Both its config and its `run.sh` live on
the drive. Moving the port from one to the other doesn't stop it travelling. The
split only pays off when the service is machine-local and the mailbox isn't —
a synced or shared volume, which is the shared-device issue's territory, not the
drive's.

## The version I'd argue for

Keep **one file, in the mailbox**, and let it state the mailbox's own answer for
everything — including a port. Then let the service file **override** the
machine-specific keys, by exporting environment variables in its run script.
Those run scripts already export `HOME`, so the mechanism is there and has
precedent.

That gets you:

- Config in the mailbox, which kills the slug, the path-mangling escaping, and
  the two-copies-of-one-transform class of bug outright.
- Hand-launching and the drive keep working untouched — no service, no
  override, config wins.
- A synced mailbox works: each machine's service says `RMAIL_PORT=…` and the
  shared config's port is just the default nobody uses.
- The installer's collision check keeps reading configs, because configs still
  carry a port.

Precedence is explicit rather than a fallback chain, and the daemon logs which
source each machine-specific setting came from at startup — so "why is it on
that port" is answerable from the log.

One question decides the shape, and it's yours to make: **when a service file
overrides the port, should the daemon say so and carry on, or should a mailbox
that has been claimed by a service refuse to start from its own config at all?**
The first is forgiving and lets you hand-launch a serviced mailbox for

symbols sit in its **dynamic symbol table**, and the dynamic linker resolves the

it was written to talk to. I tried `-Wl,-E` to force symbol export; still fails,

and the unused API functions were never pulled in to be exported.
